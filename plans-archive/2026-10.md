## Item: Account profiles ("segment envs, use different logins")
**Status:** done 2026-10-28 (daemon, script, web; profile-probe 24/24, codex-control-probe 40/40). Deviations from the first sketch below: per-profile usage view not built (see Usage view); `profile_login` runs `claude auth login` (not the TUI + /login) and `codex login --device-auth` (headless).

Several logins per agent (personal + work Claude, more than one Codex), each session under one profile, all watched at once. Both CLIs keep everything per directory: Claude Code under `CLAUDE_CONFIG_DIR` (credentials `.credentials.json`, `.claude.json`, `projects/` transcripts, settings; verified on 2.1.312: a throwaway dir gets `.claude.json`, `sessions/`, `cache/`, ~/.claude untouched, the TUI opens on the onboarding theme picker), Codex under `CODEX_HOME` (`auth.json`, `sessions/` rollouts, its own app-server; verified on 0.165: `CODEX_HOME=<empty> codex login status` = "Not logged in", ~/.codex untouched).

**Config.** `profiles: [{ id, label, agent: 'claude'|'codex', home, env?, env_file? }]` in config.json. Two implicit default profiles are always present: `claude` (home = code_home) and `codex` (home = the resolved Codex home); an existing config works unchanged and the defaults cannot be removed or shadowed (a configured profile with a default's id or home is skipped with a warning). Ids `[a-z0-9][a-z0-9_-]{0,31}`; `home` absolute (`~` expanded). `env` = non-secret variables; `env_file` = a 0600 KEY=VALUE file outside the repo (default `~/.companion/profiles/<id>.env`) for API keys, never read by the daemon except to check it exists and which KEY names it sets (for login state); the value never enters config.json, tmux's environment, argv or a log. The registry (`daemon/src/profiles/`) re-reads the config file when its mtime changes (checked on the watcher's 5 s refresh, a stat only), so `bin/companion profile add` needs no daemon restart.

**Discovery (per root).** A session's profile = the `CLAUDE_CONFIG_DIR` / `CODEX_HOME` in `/proc/<agent pid>/environ` (else the pane shell's, else what the app launched it with), matched to a profile by real path; unset or unknown = the agent's default profile. One fs read per pid, cached by pid + start time, no subprocess.
- Claude: one chokidar watcher, one `<home>/projects/**/*.jsonl` pattern per Claude profile (added / removed when profiles change). The watcher's path keys stay the bare encoded cwd for the default profile; another profile's key is `profile:<id>:<encoded>`, so two sessions in the same folder under different logins never share a key. Every place that turned a key into a directory (transcript path, project dir, /proc fd match, missed-transcript scan, chain, ensureConversationLoaded) resolves the key's profile home.
- Codex: one `CodexRolloutIndex` per Codex profile; each pane uses its profile's index.
- Subagents: one `SubagentDiscovery` per Claude profile root into the shared tracker. `get_conversation_file` accepts any Claude profile's projects dir. Herald `search_memory` reads every Claude profile's `projects/*/memory`.
- Mappings / snapshot stay under the default code_home; entries record `profileId` (mappings: `profiles` map; snapshot: optional field).
- Summary sessions carry optional `profileId` (only for a non-default profile) + `profileLabel`.

**Spawn.** Optional `profileId` on `create_tmux_session`, `scaffold_open_session` and Herald `propose_spawn_session` (agent = the profile's; an explicit agent that disagrees is refused). Default Claude profile = exactly today's launch (no `CLAUDE_CONFIG_DIR`); default Codex = `CODEX_HOME` as today. Other profiles: `CLAUDE_CONFIG_DIR` / `CODEX_HOME` + `env` through `tmux new-session -e`; with an env file the typed line is `<daemon>/scripts/profile-exec.sh <env file> <launch command>` (POSIX sh: `set -a; . file; exec "$@"`; works from bash or fish), so secrets reach only the agent process. Saved tmux configs keep `profileId` (recreate / switch).

**Login from the app.** `profiles_list` -> `{ profiles: [{id,label,agent,home,isDefault,loginState,envKeys}] }` with `loginState` `logged_in` (Claude `.credentials.json` / Codex `auth.json` exists; never read) | `api_key` (env / env file sets ANTHROPIC_API_KEY or OPENAI_API_KEY; names only) | `logged_out`. `profile_login {profileId}` spawns a tagged tmux session `login-<id>` in the profile env (Claude: `claude`, the user picks a theme and runs /login; Codex: `codex login`), gated like `create_tmux_session`. A login screen is `starting`, never a hang.

**Script.** `bin/companion profile list|add|remove|login|env-path` (`add <id> --agent claude|codex [--label L] [--home DIR] [--share|--no-share]`): creates the home (0700), optionally symlinks the shared non-secret bits from the default home (Claude: CLAUDE.md, settings.json, skills, agents, commands, hooks, plugins; Codex: config.toml, AGENTS.md, skills, prompts; never credentials, projects/sessions or history), writes the config entry. `login <id>` prints the exact command and, with `--tmux`, starts the login tmux session. `remove` drops the config entry and leaves the home on disk.

**Web.** `ProfilePicker` in New Session / New Project replaces the Claude/Codex row only when more than the two default profiles exist (otherwise unchanged); a profile badge next to the Codex label (sidebar, mobile list, SessionView header) for non-default profiles; Settings > Accounts list with login state and Log in. Protocol: optional fields only (`profileId`, `profileLabel`); new requests `profiles_list`, `profile_login`.

**Usage view.** Not built: the daemon has no usage-dashboard request today (`OAuthUsageFetcher` only feeds the 5-hour alert monitor, on the default profile's credentials). Per profile later = one fetcher per Claude profile home + an optional `profileId` on a new request. Codex: no local usage API.

**Not covered:** concierge / remote_dispatch stay on the default profile; Herald knowledge besides memory; the review ledger is path-based and needs nothing.


## Item: Impact metrics + perf batch A
**Status:** batch A done + deployed 2026-10-15 (production unit drop-in `companion.service.d/perf.conf`: `UV_USE_IO_URING=0`, `Nice=5`); batch B done + deployed 2026-10-15 (daemon restart + herald-voice restart)

Measure and cut what Companion costs the box while Claude Code runs.

### Metrics (`daemon/src/impact/`)
- `sub.ts`: `runSub` / `trySub` / `runTmux` (execFile, never a shell, SIGKILL timeout, bounded buffer), each call recorded per kind (`tmux:capture-pane@herald`, `git:diff`, ...): count, duration histogram, timeouts, failures, in-flight peak. GitRunner records into it; `trackedExecAsync` covers the remaining legacy `exec` call sites.
- `sampler.ts`: every 10 s CPU + RSS/swap from /proc for the daemon, herald-voice, the tmux server and companion MCP node processes, system swap, `monitorEventLoopDelay` p50/p99/max; every 30 s one timed `tmux display-message -p '#{pid}'`; console lines counted.
- `registry.ts`: 1-minute buckets, 24 h ring, saved hourly + on shutdown to `~/.companion/impact.json` (`COMPANION_IMPACT_FILE`); counters for transcript parses (bytes, ms, full vs tail), git index.lock errors, input collisions (placeholder for batch B).
- Protocol `daemon/src/impact/protocol.ts` <-> `web/src/types/impact.ts` (mirror test); request `get_impact`. Web: Impact section in Help > Diagnostics (`ImpactDiagnostics.tsx`, fetch on open + every 10 s, 24 h sparklines, threshold flags: loop p99 > 100 ms, daemon CPU > 10 %, tmux probe > 50 ms, any subprocess timeout, swap > 90 %, any typing collision).

### Fixes
- Root cause of the 13-15 % system time: production runs `/usr/bin/node` 18 linked to the system libuv 1.48, whose io_uring SQPOLL kernel thread (`iou-sqp-<pid>`) busy-polls after every fs op; chokidar's 100 ms polling kept it awake (~90 % of the daemon's CPU). Unit template (`cli.ts`) and `bin/companion` now set `UV_USE_IO_URING=0` and the template `Nice=5`.
- chokidar: native fs events instead of 100 ms polling + awaitWriteFinish (`COMPANION_WATCH_POLLING=1` restores polling); debounce now has a 1 s max wait; safety nets: the 5 s stat reconcile of tracked files + a 10 s scan for missed new transcripts in tagged project dirs.
- Incremental transcripts (`transcript-cache.ts` + `ConversationAccumulator` / `TaskAccumulator` in parser.ts): tail reads from a byte offset, partial lines kept, inode change / truncation / rewrite = full re-read; equivalence tests + a replay of all 418 local transcripts matched the full parse. Used by the watcher, get_highlights (fresh + chain), get_tasks (now async), conversation_file.
- One shared `tmux list-panes -a` (`tmux-snapshot.ts`, 2 s cache, in-flight shared, cached COMPANION_APP tag) for the watcher refresh (in-flight guarded, maps still built on the side and swapped synchronously) and every get_server_summary / list; pstree + display-message in PID detection replaced by /proc; terminal-view captures shared for 300 ms.
- Session snapshot / mappings files written only when changed; stuck normaliser linear on long tokens; polled WebSocket requests summarised once a minute (`ws-log.ts`, `COMPANION_WS_DEBUG=1` for per-message logs).

### Batch B (done + deployed 2026-10-15)
- Input-injection guard (`daemon/src/prompt-guard.ts`, `InputInjector.sendInputDetailed`): free text into the prompt box first waits while an attached tmux client pressed a key in the last 2 s (`#{client_activity}`, up to 3 s, then refuses `user_typing`), then reads the rule-bounded prompt box from `capture-pane -p -e` (live-verified on Claude Code 2.1.301: `❯\u00a0text` between two gray `─` rules; the placeholder and prompt suggestions are DIM, SGR 2, and count as empty) and refuses `prompt_has_draft` when it holds typed text. Both bump `inputCollisions`. No prompt box (choice box, permission prompt, overlay) = proceed, so `sendChoice`, auto-approval and babysit choice answers are unaffected. Overlay Escape now only fires when the prompt box is gone AND a key-hint segment says "Esc to close" / "Esc/Enter/Space to close" (conversation text no longer matches). Errors reach the web (`input_sent` / `message_sent` error code + `payload.message` -> SessionView banner via `describeSendError`) and Herald (`SessionSource.lastSendRefusal` -> action failure / babysit escalation / relay error wording: "<name> has an unsent draft in its prompt box, so I didn't type over it.").
- herald-voice: `HERALD_VOICE_IDLE_UNLOAD_S` (default 1800, 0 = off) unloads each engine after that long unused (on its own executor, then `gc.collect()` + glibc `malloc_trim(0)`), reloads on the next request (concurrent requests share one load); `/health` keeps `ready: true` (+ `loaded: false`, `idleUnloaded: true`, cached voices/sample rate) so the daemon and `bin/herald-voice status` (exit 0) treat it as up. Measured on a separate instance (port 9891, 60 s idle): fresh 863 MB, after use 1.80 GB, after unload 239 MB; first TTS after unload 1.3 s (warm 0.5 s).
- tmux scope (`daemon/src/tmux-server.ts` `startTmuxSession`): every daemon `tmux new-session` (TmuxManager.createSession, remote one-shot dispatch, concierge) starts a NOT-yet-running server via `systemd-run --user --scope --unit=companion-tmux-<...>`; a running server is untouched; plain tmux in containers / non-Linux / no XDG_RUNTIME_DIR / no systemd-run / `COMPANION_TMUX_SCOPE=0`, or when systemd-run fails. Live-verified on a private socket (server cgroup = `app.slice/companion-tmux-private-1000-*.scope`, scope gone after kill-server).
- App spawns (`session-spawn.ts`): no more `.claude/settings.json` writes; `claude --permission-mode bypassPermissions` (TmuxManager `claudeCommand`), stored as `permissionMode` in the tmux session config so recreate keeps it. Existing settings files are left alone. Live-verified on the probe (trust prompt still parks a new dir; footer "bypass permissions on").

## Item: Stuck-session detection ("Out4 looks stuck")
**Status:** done (live-verified on the probe; production needs a daemon restart)

Deterministic, no-LLM detection of sessions that are WORKING but going nowhere, with very low false positives.

### Signals (daemon `daemon/src/stuck/`, pure analysis over the parsed transcript of the current turn)
1. **repeated_failure**: the same failure signature (failing test names, compiler errors, error lines; numbers/paths/timestamps/hex normalised) >= 5 times in 30 min, spanning >= 2 min, with no later passing run of the same command.
2. **loop**: the same tool + normalised input + same normalised output >= 5 times in 15 min with no successful edit in between (polling tools / `sleep` / `watch` exempt).
3. **oscillation**: edits on the same file flipping between the same two states (A->B->A->B->A, 4 moves) in 30 min (Edit/MultiEdit old/new pairs, Write content hashes).
4. **no_progress**: working >= 30 min with no successful edit and no new assistant text; exempt while a Bash call is pending with a changing pane, or a known long command (build/install/test) or a subagent is pending, up to 90 min.
5. **stalled_tool**: one pending tool call older than its kind's cap (Bash 20 min, others 10 min; Task/Agent exempt) and the pane unchanged across two captures >= 4 min apart; a choice/approval prompt on screen = blocked (the inbox owns it).

### Design
- `StuckDetector` fed by watcher `conversation-update` / `status-change` (debounced 1 s per session) + a 60 s tick for time-based signals; bounded state (LRU sessions, capped findings / snoozes / dismissals).
- Pane captures only through a guarded probe: per-session in-flight dedupe, 2 s timeout + SIGKILL (`defaultCapturePane`), liveness check against the watcher's live session list, at most 2 captures per tick, >= 2 min between captures of one session.
- Findings `{id, sessionId, sessionName, kind, severity, signature, summary, headline, evidence (redacted), firstSeen, lastSeen, count, turnId}`; dedupe per session+kind+signature; auto-clear when the session goes idle/waiting, the user sends a prompt (new turn), the failure stops recurring (a later run of the same command no longer shows it, or nothing for 15 min), an oscillating file moves on to a third state, or an edit lands (loop / no_progress).
- Snooze per session+kind (default 30 min), "Not stuck" suppresses the signature for the rest of the turn.
- Protocol `daemon/src/stuck/protocol.ts` <-> `web/src/types/stuck.ts` byte-identical (mirror test). WS: `stuck_list`, `stuck_snooze`, `stuck_dismiss`, `stuck_ask`, `stuck_interrupt`, `stuck_get_settings`, `stuck_set_settings`; global event `stuck_update`.
- Settings persisted in `~/.companion/stuck/settings.json` (`COMPANION_STUCK_STATE_DIR`), quiet hours (escalation config) keep findings off the Herald inbox.
- Herald: inbox item with `stuck` field (own `stuck` tone, active device only, never spoken unasked; Gaming = tone only), brief-me line "Out4 looks stuck: same test failing 6 times.", brain tools `stuck_sessions` + `snooze_stuck`, actions via ask-a-session (`relayAsk`), `propose_interrupt` (echo tier) and show.
- Web: amber "Stuck?" badge (sidebar + mobile list), dismissible SessionView banner (summary, expandable evidence, Ask what's wrong / Interrupt / Snooze 30m / Not stuck), settings card in Notification Settings (toggle, no-progress minutes, Advanced thresholds).
- Parser: `ToolCall.isError` (optional) from `tool_result.is_error`; `status` unchanged (an `error` status would start firing error-detected escalations).

## Item: Voice Front Layer (working name) — fleet-wide chief of staff
**Status:** in-progress — Phases 1 (text, named "Herald") and 2 (voice: neural TTS, push-to-talk
STT, voice interrupt, "Hey Jarvis" wake word) are merged to `main` and **deployed to the production
daemon (9877/9878) on 2026-09-30**: anthropic provider (`claude-haiku-4-5`), key via
`bin/companion install-secrets`, voice service as the `herald-voice` systemd user unit
(`bin/herald-voice install-unit`). The 9887 sandbox and its Tailscale :9890 front were retired; its
conversation was carried over to `~/.companion/herald/state.json`. Native apps still need an `/apk`
rebuild for the Herald UI (no native mic path yet). See "Phase 2 progress" below. Phases 3-5 planned.

### Goal & Rationale
A fast, always-available conversational entity layered **over** Claude Code sessions across the whole
fleet — the "Iron Man / JARVIS" experience; the bar is "no compromises". Two layers:
- **Deep layer** = the real Claude sessions: slow, heavy, do the actual work (may run 40+ minutes).
- **Front layer** = a fast/cheap model (Haiku-class, currently `claude-haiku-4-5`) that knows
  **about** the work but never does deep work or gives deep answers. A chief of staff. The user talks
  to it (voice via Wispr Flow or its own STT, or typed), it talks back (TTS or text).

Naming: final name TBD. Must NOT reuse "concierge" — that already names the shipped Global Concierge
(`daemon/src/handlers/concierge.ts`, `ConciergeView`, `concierge_open`), which is a *deep* Claude
session that fans work out. The front layer is the opposite: shallow, fast, talks about work.

Builds directly on **Item: Fleet (Inbox → Missions → Routing → Health)** above — the Fleet Inbox
(`get_fleet_inbox`, attention classification, synced `seenUpTo`) is exactly the prioritized inbox
this layer narrates and acts on. Together they are the differentiator vs Anthropic Remote Control
(single-session, no cross-machine awareness, no voice front layer).

### Behaviors
1. **Announce.** "Companion session finished; deploy session is blocked on a question." Waits for a
   gap — never talks over the user. Priority: **blocked-on-input > finished > progress**.
2. **Triage by depth, on request:** one-liner → gist → full read.
3. **Rewrite for ears.** Never read raw markdown, code, paths, or tables aloud; paraphrase ("changed
   the input injector"). Full verbatim only when explicitly asked.
4. **Relay / act.** "Tell it go ahead but skip tests" → `send_input` on the right session, then reads
   back a confirmation.
5. **Instant state lookups:** how long it has been running, what it was doing, what is waiting.
6. **Grounded.** May only paraphrase what sessions actually said. Past that: "I don't know — want me
   to ask it?". **Hallucinated status ("yeah, it deployed") is the #1 risk** — every status claim must
   trace to a session turn / inbox item fetched in this conversation.

### Guardrail Tiers for Actions
The user explicitly wants it to act — with guardrails for both *unclear/unsure* and
*dangerous-even-if-fairly-sure*.

| Tier | Examples | Behavior |
|------|----------|----------|
| **Free** | status, summaries, reads, inbox listing | Just do it. |
| **Echo** | answering an AUQ, "continue", "option 2" | Read back once with session name ("Telling *deploy* option 2, skip tests"); send unless the user says no/wait. |
| **Clarify** | ambiguous target (multiple sessions waiting), low STT confidence, utterance matches no option | Ask. Never guess. |
| **Hard confirm** | deploy, restart (incl. companion daemon), push, delete, force, prod, AJ's box, anything irreversible | Explicit confirm phrase or on-screen tap, even at 99% confidence. |

- **Danger is detected from BOTH sides:** the user's utterance AND the content of the pending
  question. If the session asks "deploy to prod?", a casual "yeah" gets hard-confirm.
- **Never silently batch.** "Tell them all to go ahead" → safe ones proceed (echoed), dangerous ones
  are split out and confirmed individually.
- Daemon restarts inherit the project hard rule (Fleet C6): per-daemon, explicit sign-off, never
  batched.
- Danger classification should be a pure, unit-testable function (keyword/pattern list + pending
  question text + target host), not left solely to the model's judgment; the model can escalate a
  tier but never lower one the classifier set.
- Every action (and its tier + confirmation) goes to the existing audit log
  (`daemon/src/audit-log.ts`).

### Architecture
- **One entity across the whole fleet** (all daemons), single prioritized inbox.
- **Brain runs server-side on a hub**, not on a device, so the conversation persists across devices;
  devices are just mic + speaker endpoints. Device handoff: conversation follows you desk → phone →
  iPad.
- **Inputs already exist:**
  - daemon session state + waiting-for-input detection — `daemon/src/parser.ts`
    (`isWaitingForChoice`, `extractHighlights`, `detectActiveChoicePrompt`);
  - pending AUQ via tmux-pane scraping (not on disk until answered — see `parseTextChoicePrompt`);
  - last-turn text (`get_highlights` / `get_full` in `daemon/src/websocket.ts`);
  - input injection — `send_input` in `daemon/src/handlers/input.ts` → `daemon/src/input-injector.ts`;
  - multi-daemon connections — `web/src/services/ConnectionManager.ts` (client side) and the
    `companion-remote` MCP (`mcp/src/`, `mcp/README.md`: `remote_list_sessions`,
    `remote_get_conversation`, `remote_send_input`, ...) for hub-side cross-daemon access;
  - Fleet Inbox (planned, Fleet Phase 1) for attention-sorted, seen-aware items.
- **Brain tools** (thin wrappers over the above): `inbox()` / `list_sessions()`,
  `summarize(session)`, `read_full(session)`, `send_input(session, text)`. Summaries are produced by
  the front model from fetched text; `read_full` returns verbatim for "read it to me" requests.
- **Pipeline:** STT → Haiku brain (tool use, Anthropic API) → TTS. Wispr Flow is one input path
  (great for dictation into text fields) but hands-free needs its own STT.
- **Hub placement (TBD):** likely a new daemon-side module (or sibling service) on one designated
  daemon, reaching the rest of the fleet the same way the concierge does (companion-remote /
  per-origin tokens). Clients connect to the hub over the existing WS protocol with new additive
  message types (Fleet C2/C3 apply: additive, feature-detected, zero cost when off).
- **Notification interplay:** announcements should coordinate with `daemon/src/escalation.ts`
  (browser → push) so the same event is not both spoken and pushed; an event heard/acknowledged via
  voice should mark it seen (Fleet `mark_seen`).

### Hardware / Hosting
User wants to use their own hardware; if usage is modest, a Mac mini or DGX Spark is an acceptable

- Local STT (Whisper-family, e.g. faster-whisper) on a GPU box / Spark for latency + privacy.

### Usage Contexts & Devices
- **Desktop (FIRST voice target).** Gaming headphones with boom mic are primary (no echo problem).
  Studio mic is a bonus (needs echo cancellation or self-mute while speaking). Killer use case:
  gaming while sessions work — chime in ear, push-to-talk on a hotkey / mouse button (user is often
  on Discord voice, so no wake word while gaming), "later" snoozes the queue. Wake word + hard mute
  as options outside gaming.
- **Phone + earbuds.** Walking around the house; push-to-talk via earbud tap. iOS background mic is
  restrictive — needs native audio background-mode work in a Tauri plugin (alongside
  `desktop/src-tauri/plugins/`).
- **Park with iPad nearby.** Works whenever the device has connectivity (cellular/hotspot); daemons
  reachable via existing tailnet/HAProxy routes.

### Phase 1: Discovery + pairing (built)

**Daemon identity.** `~/.companion/daemon-id.json` holds a stable random id (16 bytes hex, created
on first start, 0600). Display name = config `name`, else `Companion on <hostname>`.

**mDNS.** `_companion._tcp`, instance name = display name, unchanged `mdns_enabled` switch. TXT:
`id` (daemon id), `name`, `version` (daemon package version), `pairing` (`1`/`0`), `tls` (`1`/`0`),
`port`, `proto=1`, `ip` (up to 3 LAN IPv4s from physical interfaces: hosts with docker / VPN bridges
advertise dozens of addresses, so the app tries the hint first and uses the first address that
answers `pair_hello`). Never a token, code, OTP or path. A unit test asserts the TXT holds no
listener token and only those keys.

**Device registry.** `~/.companion/devices.json` (0600, atomic temp+rename, dir 0700):
`{version:1, devices:[{id, name, platform, createdAt, lastSeenAt, salt, tokenHash, via, capabilities?}]}`.
Token = `cdt1.<deviceId>.<43 chars base64url = 256 random bits>`; stored as
`sha256(salt || secret)` with a 16-byte per-token salt, compared with `timingSafeEqual` (a dummy
compare runs for unknown ids). scrypt buys nothing for 256-bit random secrets and would cost CPU on
every reconnect. `lastSeenAt` writes are coalesced (at most one disk write per minute). Revoke
deletes the entry (the audit log keeps the history). Trigger tokens stay a separate registry
(`herald-trigger-tokens.json`, triggers only); the two share the hashing / constant-time helpers,
not the file, so a trigger credential can never become a full one.

**Pairing protocol.** Unauthenticated sockets may send exactly `pair_hello`, `pair_request`,
`pair_confirm`, `pair_redeem_qr`; everything else still answers "Not authenticated".
- `pair_hello` -> `{daemonId, name, version, pairing, tls}` (no secrets; lets a browser show what it
  is pairing with).
- `pair_request {deviceName, platform, publicNonce}` -> `{pairingId, expiresAt}`. The daemon makes a
  6-digit code (`crypto.randomInt`), 2-minute expiry, bound to the requesting socket (a dropped
  socket cancels the request). The code goes to: the journal (`Pairing: "Chris's iPad" (ios) wants
  to pair - code 123456`), `bin/companion pair`, and a `pair_pending` broadcast to authenticated
  clients (name, platform, code, address, expiry).
- `pair_confirm {pairingId, code}` (same socket) -> `pair_result {status:'approved', token,
  deviceId, daemonId, daemonName, publicNonce}`; the token is sent once and never stored in clear.
- `pair_approve {pairingId}` / `pair_deny {pairingId}` from an authenticated client (or the CLI)
  push the same `pair_result` (approved / denied) to the waiting requester.
- QR: `pair_qr_create` (authenticated, or `bin/companion pair --qr`) -> one-time secret (32 bytes,
  10-minute expiry, single use, at most 5 outstanding) as
  `companion://pair?host=..&port=..&tls=0|1&id=<daemonId>&name=..&otp=..`. `pair_redeem_qr {otp,
  deviceName, platform}` issues a device token without the code step. The web shows the QR as a
  daemon-rendered PNG data URL (no QR library in the web bundle).
- Limits: 5 wrong codes per pairingId then locked; 10 pending globally; 3 pending and 10 requests
  per 10 min per IP; per-IP exponential backoff after wrong codes / bad OTPs (2^n s, cap 5 min,
  forgotten after 15 quiet minutes); 50 wrong codes daemon-wide in 10 min suspends code pairing for
  10 min. Every request / confirm / approve / deny / QR create+redeem / revoke / rename / upgrade is
  audit-logged (never the code, OTP or token).
- Network trust: `pairing: false` disables it. Code pairing (`pair_request`) is accepted only from
  loopback, RFC 1918, link-local, CGNAT/tailnet 100.64/10 and IPv6 ULA/link-local, unless
  `pairing_allow_public: true`. Behind a reverse proxy the X-Forwarded-For client is used (only when
  the peer itself is trusted), so the public HAProxy route counts as public. QR redemption works from
  anywhere: the OTP is a 256-bit secret the user handed over on purpose.

**Auth.** `authenticate` accepts a device token (scope full, `authKind:'device'`) or the listener
token (`authKind:'legacy'`, unchanged, documented as legacy). The response carries `authKind`,
`deviceId`, `daemonId`. Device `capabilities` narrow remote exec/dispatch/write like per-origin
credentials. Revoke closes that device's sockets immediately (`token_invalidated {reason:
'device_revoked'}`, close 4401); the client stops reconnecting.

**Management.** WS (authenticated, full scope): `devices_list` (+ `currentDeviceId`),
`device_revoke`, `device_rename`, `pair_pending_list`, `device_upgrade {deviceName, platform}`
(legacy-token client gets its own device token silently). CLI: `bin/companion pair [--qr]
[--approve ID|--deny ID]` (watches and prompts y/n/skip), `bin/companion devices
list|revoke|rename`; both talk to the running daemon over loopback with the listener token, and fall
back to editing devices.json when the daemon is down.

**Herald.** Not in Phase 1 (the stuck-session work owns the inbox right now). Follow-up: a
`pair_request` inbox item with a tone for the active device only; approval stays on-screen, never
by voice.

**Clients.**

  port, txt}`: Android NsdManager (serialized resolves), iOS NWBrowser + NWConnection to resolve the

**Threat model.**
- *LAN attacker spamming pair requests*: per-IP and global caps, prompts are deduped and expire in 2
  minutes; requests never auto-approve; pairing can be turned off; public networks refused by
  default.
- *Code guessing*: 6 digits, 5 tries per request, 3 concurrent per IP, exponential backoff, global
  suspension; the code only appears where the user already is (journal, CLI, signed-in apps), so a
  guesser has ~5e-6 odds per request and gets throttled long before 1e6 tries.
- *Replayed QR*: single-use, 10-minute expiry, stored hashed; a leaked old QR is dead. A QR that
  leaks while fresh pairs one device the user can see in Devices and revoke.
- *Revocation*: deletes the hash, closes live sockets at once, refused on reconnect.
- *Token storage on device* (built 2026-10-05): on Android and iOS the device tokens live in the
  platform's secure storage through `plugin:herald-native|secure_get / secure_set / secure_delete`
  (`web/src/services/secureTokens.ts`). Android: AES-256-GCM under a non-exportable Android Keystore
  key (`companion_secure_v1`, hardware-backed where available), ciphertext in private
  SharedPreferences, the entry name bound as associated data (`SecureStore.kt`). iOS: Keychain
  generic passwords, `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, so not synced to iCloud and
  not restored onto another device (`SecureStore.swift`). The server list in app storage
  (localStorage + tauri-plugin-store) keeps `token: ''` + `tokenStore: 'secure'`; tokens are read
  into memory once at startup. Migration on first launch: write, read back, and only then drop the
  plaintext copy; any failure (an older native build, a Keystore error) keeps the plaintext copy
  and retries next launch. Desktop and browser keep app storage (desktop: per-user app data;
  browser: the origin's localStorage). Residual risk: a rooted / jailbroken device or malware
  running as the app can still ask the Keystore / Keychain for the token while the app is
  installed; an Android backup restored onto another device cannot decrypt (the key stays behind)
  and asks to pair again. Device tokens stay per-device and revocable, which bounds the damage.
- *TXT leakage*: TXT holds id, name, version, pairing/tls flags and port only (test-enforced); the
  daemon id is not a credential.
- *Legacy token*: unchanged and still all-powerful; the app offers the one-tap upgrade, and once all
  devices are paired the user can rotate it.

### Phase 3: Push relay, secrets, wizard
**Push relay** (`relay/`, small Node service on hexinas behind HAProxy, `push.cush.rocks`):
- Holds the one Firebase service account. Daemons never get FCM credentials.
- Registration: daemon generates an Ed25519 key pair on first use, `POST /v1/daemons` with its
  public key -> relay id. Devices register their FCM/APNs token with their daemon (as today); the
  daemon sends `POST /v1/push {deviceToken, title, body, data}` signed with its key (timestamp +
  nonce, 60 s skew).
- Abuse limits: per daemon 60 pushes/hour, 500/day; per device token 30/hour; at most 20 device
  tokens per daemon; registration rate-limited per IP (5/day); unknown or revoked keys refused; an
  admin can ban a daemon id.
- Privacy: payload carries the session name and at most a 100-character preview; daemon setting
  `push_preview: false` sends only "Session needs input"; the relay logs counts, not bodies, and
  keeps no payloads. PRIVACY.md updated.
- Self-hosters keep `fcm_credentials_path` (direct FCM wins over the relay).

### Audit of the current path (2026-10-14)
`daemon/src/subagent-watcher.ts`:
- **Polling glob over all history** (`:78-92`): chokidar `usePolling` on `projects/**/subagents/*.jsonl`
  at 1 s. Polling = one `fs.watchFile` stat loop per matched file, and files are never deleted: 535
  subagent files on this box today (497 MB in files > 20 MB) = ~535 stats/s forever, growing.
  The 10-min initial-scan guard (`:128-139`) only skips the parse, not the watch.
- **Full sync re-read + re-parse on every change** (`:182-187`): `readFileSync` + `split` +
  `JSON.parse` of every line, per change event, on the event loop. O(n^2) over an agent's life; a
  100 MB transcript blocks the loop for seconds per append. `fileKeyIfTracked` is a linear scan
  (`:175`).
- **Wrong completion, latched forever.** (a) "last assistant entry is text without tool_use" =
  complete (`:240-270`), but Claude Code writes each content block as its own entry: in the last 150
  subagent files a text-only assistant entry is followed by a tool_use entry 592 times. If a change
  event lands between them the agent flips to complete and the latch (`:152-156`) keeps it there.
  (b) `stop_reason: 'end_turn'` is set mid-file 95 times (agents resumed via SendMessage keep
  writing) and also latches. (c) `getAgentTree` calls anything quiet for 5 min complete (`:306-308`):
  a subagent waiting on a 6-min test run shows "done". (d) `status: 'error'` exists in the type but
  is never produced; failed agents show as completed.
- **Metadata ignored**: `.meta.json` (`agentType`, `description`, `toolUseId`, `spawnDepth`,
  `requestShape`, `worktreePath`, `stoppedByUser`) is never read; `subagentType` is a hard-coded
  `''` (`:196`), `description` is the first 100 chars of the prompt, `slug` is absent in ~25 % of
  files. No parent/child link, so no tree.
- **Events emitted into the void**: `agent-started/-completed/-update` (`:162-167`) have no
  listeners anywhere; clients only poll.
- **`getAgentDetail`** (`:359-401`) runs `parseConversationFile` = another full sync read of the whole
  file (`parser.ts:221`) per request; matches by agentId only.
- Memory is fine (small records, 24 h cleanup `:58`).

Web:
- `useSubAgents.ts` polls `get_agent_tree` every 2 s (5 s idle) per open SessionView and sets state
  every poll even when nothing changed (re-renders the whole DispatchPanel, re-sorts).
- `useSubAgentDetail.ts:63-65`: interval is chosen once from a ref initialised to `'running'`, so it

- Every `Agent` tool_result is `toolUseResult.status: 'async_launched'` (116/116, foreground and
  background alike). **The parent's tool_result is NOT a done signal.**
- The definitive signal is a parent `type:'user'` entry whose text holds
  `<task-notification><task-id>{agentId}</task-id><tool-use-id>…</tool-use-id><status>completed|failed</status><summary>…</summary>[<usage><subagent_tokens>…<tool_uses>…<duration_ms>…</usage>]`
  (784 seen: 724 completed, 60 failed). It fires each time the agent stops; a resumed agent
  (SendMessage) writes again and later notifies again. Background Bash tasks use the same envelope
  (task-id is not an agent id: match on known agent ids only).
- No `TodoWrite` / `TaskCreate` tool_use appears in any recent transcript (main or subagent; this
  harness does not expose TodoWrite to agents). Checklist progress must be optional input, not the
  backbone.
- Assistant entries carry `message.usage` (input / cache / output tokens) and `stop_reason`.
- Nested agents: meta has `spawnDepth` (all 1 so far) + `toolUseId` = the spawning tool_use id in the
  parent's (or parent agent's) file; files are flat in `<conv-id>/subagents/`.

Reusable: `review/jsonl-tail.ts` (async byte-offset tail, carry, shrink/inode reset, 8 MB line cap,
per-read budget), `review/sources.ts` (`listSubagentFiles`, cached `.meta.json` reads; note its
`sort().slice(0, 200)` drops arbitrary agents past 200 because ids are random), stuck
`normalize.ts` (`analyzeFailure`, `inputKey`, `commandCore`, `isLongCommand`, `isPollingCommand`)
and `signals.ts` `analyze()` (pure over a `StuckDigest`, so a digest built from subagent events
works without the parser), Herald `polishGists` metering pattern (`herald/service.ts:2059`,
`onUsage`), `syncStuckAlerts` inbox pattern, `HeraldToolDeps.stuck`-style late-bound tool deps
(`herald/tools.ts:584`), redaction in `herald/knowledge/redact.ts`.

### Design
New module `daemon/src/subagents/` replacing the inside of `SubAgentWatcher` (class name and the
`get_agent_tree` / `get_agent_detail` responses kept, fields only added).

1. **Discovery without polling the past** (`discover.ts`). No glob watch. The set of *candidate
   conversations* = conversations the main watcher has seen written in the last 30 min, plus any
   conversation that still has a running agent (cap 32). For each: one `fs.watch` (inotify / FSEvents)
   on `<conv-id>/subagents/` (created lazily: when the dir does not exist yet, re-check on that
   conversation's next `conversation-update`, debounced). A dir event = readdir of that one dir
   (debounced 250 ms). Backstop: a 5 s tick stats ONLY files of agents in `running` state (size
   compare; read only on growth) because fs.watch can drop events. Files older than 10 min at
   discovery are registered as history (meta only, no tail) unless the parent says they are live.
2. **One incremental reader per subagent file** (`tracker.ts`): `JsonlTail` from `review/`, read
   budget per pass (4 MB per file, 16 MB per tick overall), a new 100 MB file is read in slices across
   ticks with `setImmediate` yields; never `readFileSync`. Each entry folds into a small fixed-size
   `AgentState` (below) and is then dropped: nothing keeps raw lines.
3. **Parent-side signals** come from the conversation the agent belongs to: the tracker runs one
   cheap `JsonlTail` on each candidate parent file but only does a substring test (`task-notification`,
   `"name":"Agent"`) before `JSON.parse`, so the parent tail costs a scan, not a parse. (Phase 3 may
   hand those lines over from the review ledger instead, see Sharing.)
4. **AgentState (bounded, per agent)**: ids (agentId, sessionId, parentToolUseId, parentAgentId,
   depth), meta (type, description, background, worktree, model), timings (startedAt, lastEntryAt,
   lastToolAt, endedAt, elapsed), status (below), counters (tool calls by name, edits, files touched =
   capped set 50 with counts, Bash runs, tests run / passed / failed from `analyzeFailure` + test
   command detection), tokens (sum of `usage`, plus the notification's `subagent_tokens` when
   present), current activity (pending tool name + display, last assistant text clipped 160), last 40
   timeline events (ring: tool + display + ok/fail + at), optional checklist (latest TodoWrite /
   TaskCreate/TaskUpdate input, or `Step N/M:` text lines, see CLAUDE.md line), a stuck digest ring of
   `StuckToolEvent` (MAX 200) for signals, notification summary + result excerpt (clipped 600).
   Memory budget: ~16 KB per agent, LRU 300 agents, finished agents evicted 24 h after end (state
   rebuilt from the file if asked later).
5. **Nesting**: parent = the agent whose file contains a tool_use with id == child's
   `meta.toolUseId` (index tool_use ids of `Agent` calls per file as they are tailed); depth from
   `spawnDepth`. Tree rendered by parentAgentId.

### Completion detection
State machine per agent: `starting -> running -> (waiting_child) -> done | failed | stopped | lost`.
- **done / failed**: the parent's `<task-notification>` with this agent id (status completed/failed;
  `meta.stoppedByUser` -> `stopped`). Definitive; carries summary + usage.
- **resumed**: new sidechain bytes after a notification whose timestamp is later than it ->
  `running` again (no latch; a resumed agent must show as running).
- **quiet-but-alive**: no notification, a tool_use pending -> `running` with the pending tool shown
  (a 20-min test is not "done"). Pending `Agent` call -> `waiting_child`.
- **probably done** (only when the parent file is unreadable / not candidate): last assistant entry
  has `stop_reason: 'end_turn'` AND no new bytes for 30 s -> `done?` (shown as "finished
  (unconfirmed)"), upgraded by the notification when it arrives.
- **lost**: no notification, no bytes for 30 min, no pending tool -> `lost` (never silently "done").
Text-only assistant entries never complete an agent.

### Stuck signals for subagents
Feed the agent's `StuckToolEvent` ring into `stuck/signals.ts` `analyze()` with `phase:'working'`
and `pane: null` (so `stalled_tool` needs no capture: replaced by "pending tool older than its cap
with no bytes written", since a subagent has no pane). Reuses repeated_failure / loop / oscillation /
no_progress thresholds from stuck settings. Evaluated on the tracker tick only for running agents,
never on a pane, never a subprocess. Findings are `AgentState.stuck` (kind + headline), not
`StuckDetector` findings (no session banner); they feed the inbox below.

### "Where's it at" rollup
- `facts.ts` (pure): one compact JSON per dispatch group (agents of one session's turn, or one
  agent): status counts, per agent {name, type, status, elapsed, idle, checklist x/y, current
  activity, last 3 events, tests pass/fail, files touched count + top 5 basenames, stuck headline,
  notification summary}. All strings through `redact.ts` + clipped. No raw transcript ever.
- **Deterministic answer first** (`rollupText(facts)`): "3 of 5 done. Bob is running tests (2 failing,
  4 min). Ann is idle 6 min on a Bash call." Free, always available; it is what Herald's fallback
  brain and the MCP tool return when the LLM is off.
- **LLM polish (optional)**: `HeraldService.polishRollup(facts)` modelled on `polishGists`: one
  tool-less call, `maxTokens` ~200, 20 s timeout, `onUsage` metering, budget + brain-offline checks.
  Triggered only (a) on demand (Herald tool, page "Summarize", MCP with `polish: true`) or (b) on a
  material state change (an agent finished / failed / turned stuck) while some client has the status
  page open, throttled to <= 1 per minute per group, cached by a facts hash. Setting
  `subagents.rollup_llm`: `off | on_demand | auto`, default `on_demand`.

### Performance budget / non-impact guarantees
- **Strictly less I/O than today**: chokidar polling over every historical subagent file is removed
  (535 stats/s -> fs.watch on <= 32 dirs + <= 1 stat per running agent per 5 s). Full re-reads and
  sync parses are removed (each byte read once, async, budgeted).
- **No subprocesses**, ever (no git, no tmux capture, no shell).
- **Nothing added to the `conversation-update` hot path** except a debounced "is this conversation a
  candidate / does its subagents dir exist" check (Map lookup + at most one async stat per 2 s per
  conversation).
- **Budgets per tick, not lifetime**: <= 16 MB read and <= 20 ms of synchronous fold work per tick,
  then `setImmediate` yield; a 100 MB backlog is caught up over several ticks with the newest-first
  rule for live agents (tail the last 2 MB of a never-seen huge file first for "current activity",
  backfill counters lazily, mark `partial: true` until done).
- **Bounded memory**: fixed-size AgentState, rings, LRU 300, eviction 24 h; parent notification index
  capped; meta cache reused from `review/sources.ts`.
- **Client traffic**: deltas only, only to watchers, 1/s coalescing; no polling while watching; detail
  highlights only for the focused agent.
- **LLM**: never on a timer, never without a client asking or a watcher present; <= 1/min/group;
  cached by facts hash; metered and budget-gated; off-able.
- **Kill switch**: config `subagents.enabled` (default true) + `subagents.discovery: 'watch' |
  'legacy'` to fall back to the old watcher if fs.watch misbehaves on a platform.
- Guard tests: a perf test feeding a 100 MB synthetic file asserts no single fold step > 50 ms and
  total reads == file size.

### Sharing one tail with the review ledger
The ledger tails the same subagent files (only when review is used, on its own debounce). Phase 1
keeps them separate (each byte is read at most once per consumer, async; today's watcher re-reads
everything, so this is already a large net win). Phase 3: a `TranscriptFeed` that owns one
`JsonlTail` per file and fans parsed entries out to subscribers (subagent tracker always; ledger when
present). The ledger's rebuild path (re-read from 0 on chain change) stays as is, using its own
temporary tail, so the shared feed never rewinds.
